# Digital Shadows of a Signalized Intersection

> Reconstruction and comparison of two **digital shadows** of one and the same real
> signalized intersection — one from **vision** (a traffic camera) and one from **V2I
> messages** —, projected onto a shared **SUMO** runtime and animated in a **web 3D viewer**.

Code and data repository accompanying the article *"Vision- and V2I-based Digital
Shadows of a Signalized Intersection: A Comparative Fidelity Evaluation for Smart Cities"*.

**Authors:** Pablo Barbecho Bautista · Santiago Delgado Pinos · Anthony Dominguez Chacha
· Universidad de Cuenca, Cuenca, Ecuador.

---

## Context

Traffic control at signalized intersections usually runs on fixed-time plans (inflexible in
the face of changing flows) or on actuated control, which reacts only once the vehicle has
already entered the detector zone: the controller never observes the real traffic state, only
a partial and delayed view.

A **digital shadow** answers that gap. It is a replica of the intersection's mobility state,
reconstructed in real time and updated continuously inside a simulation runtime, which an
anticipatory controller can consume instead of the raw detector signals. It is a lightweight
version of the digital twin: the flow is **one-directional** (physical → virtual), for
monitoring, without acting back on the road.

Two sensing channels can feed that shadow, and each degrades it through a different mechanism:

- **Infrastructure camera (vision):** it observes every vehicle without on-board equipment,
  but must **infer** each attribute (position, lane, class) from the pixels.
- **V2I messages:** equipped vehicles broadcast their own state (position, speed, heading,
  lane) in periodic messages that a roadside unit (RSU) collects. These are **exact and
  early** data, with no roadside detection hardware, but their coverage depends on the
  penetration of equipped vehicles and on the quality of the wireless channel (packet loss).

Which of the two channels produces the more faithful shadow is an open question: the
literature evaluates each on its own terms (vision with detection and tracking metrics in the
image plane; V2I with packet-level network metrics), rarely comparable, and neither is
measured as what the controller actually consumes: a **causal, real-time** reconstruction of
the mobility state. This work addresses that gap: it reconstructs the **same** real
intersection through both channels and compares the fidelity of the resulting shadows under a
**single metric specification**.

## The two shadows

### Vision shadow

Starting from a 180 s video from a traffic camera: **detection** (YOLOv8) → multi-object
**tracking** (ByteTrack) → **projection** onto the road plane by homography → it drives a
**SUMO** runtime directly. The usual detect–track–project flow is extended with two properties
needed to operate live:

- **Strictly causal:** it uses no future information at any step of the reconstruction.
- **Domain-aware reconnection:** it repairs track fragmentation caused by occlusion,
  conditioning on time, space, heading continuity, vehicle class, and route validity.

### Message shadow (V2I)

It reconstructs the same traffic from the periodic messages that reach the RSU, generated by
replaying an offline reconstruction over a **SUMO/Veins** channel model. The sweep covers the
broadcast rate (1, 2 and 5 Hz) and packet loss (0–50%), so that **the network is the only
degraded element** and the shadow is evaluated at the maximum fidelity the link allows.

### Comparison

Each shadow is contrasted against **its own ground truth** — hand-labeled video for vision,
the generating simulation for V2I — with the same matcher (Hungarian assignment) and the same
metrics: route and lane accuracy, delay, detection, trajectory continuity, vehicle class, and
per-approach occupancy. Which channel turns out to be more faithful **depends on the operating
point**: vision locates with minimal delay and no infrastructure, but loses precision in the
far field; the messages give exact lane and identity and hold up well against loss at 2–5 Hz,
at the cost of about one second of delay.

| | Vision shadow | Message shadow (V2I) |
|---|---|---|
| **Input** | video from a traffic camera | periodic messages to an RSU |
| **Equipment** | none on board | equipped vehicles |
| **Strength** | full coverage; minimal delay | exact lane and identity |
| **Cost** | inference from pixels; less precise in the far field | packet loss; about 1 s of delay |

## What this repository contains

A self-contained demo to **run and visualize the two shadows live together with the 3D view**
over the real site (Rusia intersection, Cuenca). The shadows are replayed from precomputed
artifacts (tracks, events and homography; see `verify_out/`), with no need to re-run GPU
detection. The 3D viewer is shared: the same page animates vision or messages, changing only
the scene and the port.

Demonstration videos of the reconstructed shadows are available on YouTube: the
**vision-based** shadow at https://youtu.be/HQz31QbtzFU and the **V2I-message-based** shadow
at https://youtu.be/nW8IE8u1a9M. This repository provides everything needed to reproduce
those demos locally.

```
├── tests/                  # tests
└── requirements.txt
```

The 3D viewer is shared by the two shadows: the same page serves vision and messages; only the
scene and the port change.

## Prerequisites

| Requirement | Use |
|---|---|
| **Python 3.10** | Everything |
| **SUMO 1.12** (`sumo`, `sumo-gui`; `traci`/`sumolib` in `$SUMO_HOME/tools`) | Both shadows (TraCI) |
| **ffmpeg / ffplay** | Vision shadow (video playback) |
| **CUDA GPU** | Only to regenerate tracks with YOLO; by default the demo replays precomputed tracks |
| **X server (`DISPLAY`)** | `sumo-gui` and `ffplay`; use Xvfb if headless |

### Python environment

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
# SUMO is not installed via pip; expose its tools:
export SUMO_HOME=/usr/share/sumo
export PYTHONPATH="$SUMO_HOME/tools:$(pwd):$PYTHONPATH"
```

In the commands below, always export `SUMO_HOME` (and `DISPLAY` for the windowed modes).

### Running on Windows via WSL2 (Ubuntu, no sudo)

Tested on WSL2 + WSLg (Ubuntu with Python 3.14 only). Use a clone **inside** the WSL filesystem
(a Windows checkout with `core.autocrlf=true` turns the files into CRLF and breaks the scripts):

```bash
git clone <this repo> ~/ds/Digital_Shadows && cd ~/ds/Digital_Shadows
bash scripts/wsl/setup_wsl.sh              # uv + Python 3.10 + deps + SUMO 1.12.0 (all under ~/ds)
scripts/wsl/run_demo.sh vision             # -> http://127.0.0.1:8301/index.html (open it in Windows)
scripts/wsl/run_demo.sh messages           # -> http://127.0.0.1:8300/index.html + 2 SUMO-GUI windows
scripts/wsl/run_demo.sh messages-smoke     # headless 30 s self-test
```

Notes: use **SUMO 1.12** (a newer one, e.g. 1.28 from pip, crashes the pipeline with exit code 245);
`ffplay` is optional (`sudo apt install ffmpeg`) — without it the shadow runs but the video window is
skipped; the md5 "provenance guard" of the demo only warns (the pins come from the authors' internal
tree; set `DS_STRICT_PROVENANCE=1` to make it abort).

To keep the repository light, two kinds of heavy input are **not versioned**. The default

| Asset | Location | How to obtain it |
|---|---|---|

## 2) Message shadow (V2I)

A single command brings up the **two SUMO-GUI windows (reality + shadow) + the 3D viewer**:

```bash
cd reconstruccion_causal
export SUMO_HOME=/usr/share/sumo
export DISPLAY=:1

# Base case (no packet loss)
CSV=inputs/cert/mc_2Hz_P00.csv PERIOD=0.5 OUT=runs/demo ./scripts/vista_dos_ventanas_3d.sh
#   -> open http://127.0.0.1:8300/index.html

# With packet loss (e.g. 40%): change the input CSV
CSV=inputs/cert/mc_2Hz_P40.csv PERIOD=0.5 OUT=runs/demo_p40 ./scripts/vista_dos_ventanas_3d.sh
```

The input CSVs `mc_<freq>Hz_P<loss>.csv` live in `reconstruccion_causal/inputs/cert/`
(frequencies 1/2/5 Hz; loss levels P00–P50).

### Reading the validation summary: `FUERA_DE_RED`

`causal_player.py` compares, after every tick, the position it commanded with the one SUMO
reports. A tick is `OK` (≤ 0.1 m), `WARNING` (≤ 0.5 m) or `FAIL` (> 0.5 m).

The input CSVs keep moving each vehicle in a straight line past the end of the three exit
approaches (`-E3`, `-E5`, `-E6` in the Rusia net), but those edges are dead ends: the net has
no road beyond them. `moveToXY` cannot place a vehicle where there is no road, so SUMO leaves
it frozen about 1 m before the lane end while the commanded point keeps going, and the gap
grows ~1.4 m per 0.1 s tick until the vehicle is removed by timeout. That is data outside the
modeled network, not a projection error of the shadow.

Those ticks are therefore reported apart, with status `FUERA_DE_RED`, and are left out of
`OK/WARN/FAIL` and of the `error_pos_m` statistics. A tick qualifies only if all of these hold:
the raw status is not `OK`, the commanded lane is a dead end (no outgoing links), the commanded
point is at or past the lane end (1.5 m tolerance for the ~1 m clamp), and the point SUMO read
lags behind it along the lane. A large error on a connected lane is still a `FAIL`.

In `summary.json` and in the console summary:

- `n_FUERA_DE_RED` — number of such ticks (`fuera_de_red` in the console).
- `error_pos_m_bruto_max` — the raw maximum, including those ticks (shown as `bruto` in the console).
- `validation_log.csv` keeps every tick, with `projection_status = FUERA_DE_RED` for them.

Example, `mc_2Hz_P00.csv` (62 vehicles, 22 000 states): before the change, `OK/WARN/FAIL =
21238/22/740` and `position_error_max = 28.47`. After it, `21238/0/0`, `fuera_de_red = 762`
(= 22 + 740) and `position_error_max = 0.081` (raw 28.47). The causality guard is unaffected.

Use `--strict-net` to restore the raw classification (nothing is reclassified).

## 3) 3D visualization

The Three.js viewer (`ws_emitter/web/`) is **vendored offline** (no CDN). It is two processes:
a static HTTP webserver that serves the page and generates `/config.json`, and a WebSocket
server embedded in each shadow's emitter.

| Shadow | HTTP | WebSocket | Scene |
|---|---|---|---|
| Messages | 8300 | 8931 | `scene_rusia.json` |
| Vision | 8301 | 8932 | `scene_vision_rusia.json` |

The viewer comes up integrated from each shadow (sections 1 and 2). To inspect only the static
page (it needs an emitter running separately to animate):

```bash
python3 -m ws_emitter.webserver --site rusia
#   -> http://127.0.0.1:8300/index.html
```
